# Product specifications

Specifications explain a proposed or agreed product decision so people can understand, discuss, and approve it. Keep them short: problem, decision, concrete examples, scope, and open questions.

## How to use them

- **Proposed:** open for discussion, not permission to change the application.
- **Accepted:** record who approved the decision and when. Implement only the agreed scope.
- Keep implementation details and test results in the related change, not in the decision document. Verify that the implementation follows the decision.
- Agents must consult relevant specifications, respect accepted decisions, and ask before changing them or adding exceptions. Instructions guide this behavior; components, tests, and CI provide technical enforcement.
